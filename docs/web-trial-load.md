## 4. 메모리 (로컬, `scripts/trial_bench/memory.py`)

기존 표는 버그였다: `max_rss_mb()`가 읽던 `resource.getrusage(RUSAGE_SELF).ru_maxrss`는 프로세스 생애 전체의 고점이라 한 번도 리셋되지 않는다. 한 프로세스에서 8개 파일을 순서대로 재면 각 행이 이전 행의 최댓값을 그대로 물려받아 61 → 1028 → 1172 → … → 1808 MB로 단조 증가하는, 개별 케이스와 무관한 숫자였다. `memory.py`를 고쳐 각 케이스를 `--worker`로 자기 자신을 재호출하는 새 자식 프로세스(겹치는 두 파싱을 수행하고 그 프로세스 자신의 peak RSS를 보고)에서 측정하도록 했다: 이제 한 행은 오직 그 파일 하나의 고립된 최댓값이고, 더는 의미가 없어진 `rss_before` 열은 없앴다.

**실제 코퍼스가 대부분 3쪽인 이유, 그리고 4쪽 행**: `~/edb-trial-bench/inputs/`의 시험지 7종은 상한이 3쪽이던 시절 `make_inputs.py`로 이미 3쪽까지 잘려 저장된 파일이라(생성 시각이 이번 상한 변경 이전) 지금 다시 재도 3쪽만 파싱된다. §6이 요구한 "과학 4쪽" 케이스는 `~/edb-trial-bench/sources/`에 있는, 아직 잘리지 않은 원본 시험지(4~20쪽, 리포지토리에는 커밋하지 않음) 중 4쪽짜리 `social_saengwoon_2020suneung_20191015.pdf`를 그대로 재서 위 표 8번째 행에 넣었다 — 코퍼스를 다시 자르는 별도 작업 없이도 실제 4쪽 케이스 하나는 이번 표에 반영된다. `sources/`의 나머지 5종(4~20쪽)까지 반영해 `inputs/` 코퍼스 전체를 4쪽으로 재자르는 일은 이번 범위 밖으로 남긴다.

**기준 대비 판정**: 기준은 2 GB의 60% = 1228.8 MB.
- 실제 시험지 8종(3~4쪽, 두 파싱 겹침)은 722.4~1114.7 MB로 기준에 114.1~506.4 MB(9.3~41.2%) 여유가 있어 **여유롭게 통과**한다(가장 빡빡한 행이 이번에 추가한 실제 4쪽 과학탐구 케이스다).
- 스펙 §6이 실제로 적은 최악 케이스는 "2×A3 **3쪽** PDF ... 2건 겹쳐"이지 4쪽이 아니다. 그 케이스를 `write_2xa3`와 동일한 지오메트리로 재현한 `2xa3_3p.pdf`는 1096.6 MB로 기준을 132.2 MB(10.8%) 밑돈다 — **스펙이 정의한 최악 케이스는 통과한다.**
- `write_2xa3`는 체험판의 실제 페이지 상한이 3→4로 올라간 것을 그대로 반영하도록 `trial_input.DEFAULT_MAX_PAGES`를 읽어 지금은 4쪽을 만든다. 이 4쪽 변형은 스펙이 정의한 케이스보다 한 단계 가혹한 별도 프로브이며 스펙의 최악 케이스가 아니다. 이번 실행에서는 1247.7 MB로 기준을 18.9 MB(1.5%) 넘었다. 경계선에 가까워 같은 케이스만 12회 더 반복 측정한 결과 1220.5~1287.8 MB(중앙값 1247.7 MB, 평균 1250.8 MB)로 12회 중 11회가 1228.8 MB를 넘었다(최대 초과 59.0 MB, +4.8%; 유일하게 기준 아래였던 1회도 8.3 MB 차이뿐). 즉 **스펙이 요구하지 않은, 더 가혹한 4쪽·2×A3 프로브에서만 경계선/근소 초과가 나타난다.**
- 위 시나리오는 모두 두 파싱이 한 프로세스에서 겹치는 경우, 즉 `TRIAL_PARSE_CONCURRENCY=2`를 모델링한 것이다. 현재 배포 기본값은 `trial_config.py`의 `parse_concurrency: int = 1`이고 §3-2도 "인스턴스당 동시 파싱이 1"이라 적었다 — 기본값대로면 인스턴스 하나는 항상 파싱 1건만 돌리므로 실제 피크는 이 표의 절반, 즉 단일 파싱 하나의 RSS에 가깝다. `TRIAL_PARSE_CONCURRENCY=2`를 켤지는 §6에서 아직 결정하지 않았다.
- 로컬 macOS 벤치(다른 프로세스가 함께 떠 있는 공유 환경)와 실측 Vercel 인스턴스 사이에는 간극이 있다: `docs/web-trial-spike-results.md`는 Vercel에서 과학 4쪽 단독 RSS 801 MB(§3 판단표), 한 인스턴스에 2건이 겹칠 때 최대 790 MB(§2-2)를 기록했다 — 둘 다 1.2 GB 기준을 넉넉히 밑돈다. 로컬 값은 그 Vercel 실측치의 약 1.4배다(실제 4쪽 로컬 1114.7 MB ÷ Vercel 801 MB ≈ 1.39, 2×A3 3쪽 로컬 1096.6 MB ÷ 2건-겹침 Vercel 790 MB ≈ 1.39) — §2-3이 시간에서 "로컬 × 4.3 ≈ Vercel"이라 쓴 것과 같은 방식의 로컬·Vercel 대응 관계이며, 메모리는 방향이 반대로 로컬이 더 높게 잡힌다. 로컬 벤치 자체의 반복 노이즈도 이 간극에 비해 작지 않다: 같은 `전자기_교재문제.pdf`를 원래 커밋(758.3 MB)과 이번 재측정(722.4 MB)에서 재면 35.9 MB(4.7%) 차이가 난다.
- **종합**: 스펙 §6이 정의한 2×A3 3쪽·겹침 2건 케이스는 1.2 GB 기준을 여유 있게 통과한다. 체험판이 상한을 4쪽으로 올리며 새로 가능해진, 스펙보다 가혹한 2×A3 4쪽 프로브는 `TRIAL_PARSE_CONCURRENCY=2`를 가정한 로컬 macOS 측정에서 경계선/근소 초과(1~5%)를 보이지만, 실측 Vercel 인스턴스(790~801 MB, 같은 종류의 2건-겹침·4쪽 케이스)는 기준을 여유 있게 만족하고, 현재 배포 기본값(`parse_concurrency=1`)에서는 두 파싱이 애초에 겹치지 않는다. "1.2 GB 기준이 안정적으로 충족되지 않는다"고 단정하기보다는, **로컬 프록시는 스펙 밖 4쪽 2×A3 극단 케이스에서 경계선에 있으나, 실측 Vercel 인스턴스와 현재 배포 설정 기준으로는 여유 있게 충족한다**는 것이 정확한 진술이다.
