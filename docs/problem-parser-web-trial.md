# 독립 문제 파서 · 웹 체험판 검토

> 이 문서는 초기 제안이다. 현재 출시 범위는 텍스트 PDF·4MB·앞 4쪽·미리보기이며, 실제 배포 설정은 [운영 문서](web-trial-operations.md)를 따른다.

- 정리일: 2026-09-14
- 상태: 제품 방향 및 초기 용량 계획. 구현·배포 결정은 별도.
- 범위: EDB 제작 앱 전체를 웹으로 옮기는 계획이 아니라, **문항 파싱만 제공하는 별도 제품 아이디어**.

## 결론

PDF·이미지에서 문항을 인식하고 검수할 수 있는 웹 체험판은 가능하다. EDB는 필수 산출물이 아니라 향후 선택 가능한 exporter로 둔다. 다만 현재 앱에서 `export_edb=False`만 지정하는 것은 진정한 parser-only 모드가 아니다. 문항 crop, 칠판용 cutout, 배치 정보 생성까지 이어지므로 파싱 코어와 출력 후처리를 분리해야 속도·용량 이득이 난다.

별도 서비스·UI로 운영할 수 있지만, 파싱 알고리즘을 두 저장소에 복사해 관리하면 개선 사항이 갈라진다. 처음에는 같은 저장소의 독립 웹 진입점 또는 버전 관리되는 공통 코어 패키지를 권장한다. 제품과 코드 저장소의 분리 여부는 별개 결정이다.

## 제안하는 경계

```text
PDF/이미지 → 전처리 → 문항 경계·번호·지문 관계·신뢰도 → 문항 데이터셋
                                                    ├─ 웹 검수/검색
                                                    ├─ 필요 시 crop/PNG/ZIP 생성
                                                    └─ 필요 시 EDB exporter
```

문항 데이터셋은 원본 문서 식별자, 페이지 번호, 원본 좌표계의 bbox, 문항 번호와 순서, 공통 지문 연결, 인식 신뢰도, OCR 텍스트, 파서 버전 및 오류/검수 상태를 보존한다. 원본 crop을 다시 만들 수 있어야 하므로 좌표계·페이지 회전·렌더 DPI를 함께 기록한다. OCR을 하지 않거나 확신이 낮은 영역은 원본 이미지 참조를 유지한다.

현 코드의 `preprocess.py`, `segment.py`, `build_structured_page_json.py`, `structured_schema.py`가 파싱 쪽 출발점이다. `build_problem_board_edb.py`의 `build_problem_entries()`에는 문항 정리와 crop/cutout 생성이 섞여 있다. 이를 순수한 문항 정규화 단계와 지연 생성되는 이미지/EDB 단계로 나누는 것이 핵심 작업이다. 기존 `run_problem_export(export_edb=False)`는 EDB 파일 쓰기를 건너뛰지만 crop/cutout·배치 경로는 그대로 수행한다.

## 성능과 용량의 근거

현재 로컬 미리보기 기록 2건은 각각 4페이지·16문항 **1.40초**, 4페이지·20문항 **1.94초**였다. 두 건 모두 OCR/AI 호출이 0회이고, 문제 crop과 칠판용 이미지를 생성한 결과다. 따라서 웹 서버나 AI가 필요한 시험지의 처리시간으로 일반화할 수 없다. 초기 파서 전용 경로에서는 칠판 렌더·배치·EDB 인코딩을 없애 추가 절약을 기대할 수 있지만, PDF 렌더링·문항 인식 자체의 비용은 남는다.

4페이지·16문항 샘플의 결과 폴더 약 9.5 MB 중 문항 crop 약 2.0 MB, 칠판용 cutout 약 1.7 MB, 발행된 EDB 약 5.7 MB였다. JSON은 수백 KB였다. 이전에 언급한 **70~80% 용량 절감은 이 샘플에 기반한 가능성**이지 전체 문서에 대한 보장치가 아니다. 원본 PDF와 bbox만 보관하고 crop을 필요할 때 생성하면 저장량은 더 줄지만, 원본 보존·개인정보 삭제 정책이 필요하다.

## 체험판의 초기 제한과 용량 계획

| 항목 | 첫 실험값 |
|---|---|
| 입력 | PDF, PNG, JPG; HWP는 후순위 |
| 1회 제한 | 3페이지, 원본 파일 합계 10 MB, 과도한 픽셀/압축 해제 크기는 별도 차단 |
| 사용량 | 계정당 하루 2~3회, 실행 중 작업 1건 |
| 출력 | 문항 JSON + 저해상도 검수 미리보기; crop/ZIP은 요청 시 생성 |
| AI | 모든 문항에 일괄 적용하지 않고 불확실한 페이지만 선택적으로 사용 |
| 보존 | 원본·결과 기본 24시간 후 삭제(정책 확정 및 사용자 고지 필요) |
| 시작 서버 | 파싱 작업자당 2 vCPU / 4 GB, 동시 파싱 1건, 작업자 2개 + 대기열 |

이 사양은 **벤치마크로 확정된 요구량이 아니라 안전한 시작 가정**이다. 하루 100~300명이 한 번씩 체험하는 정도는 검증해볼 만하지만, 동시 업로드가 몰리면 큐 대기 시간이 늘어난다. 예를 들어 작업자 2개, 실제 95백분위 처리시간 10초, 목표 가동률 50%라면 지속 처리량은 약 **분당 6건**이다. 100건이 동시에 들어오면 추가 확장 없이 마지막 작업은 수십 분을 기다릴 수 있다. AI 호출의 지연·비용·공급자별 사용 한도가 별도의 병목이다.

출시 전 실제 문서 묶음으로 OCR/AI 포함·미포함 각각의 `p50/p95` 시간, 최고 메모리, 실패율, 페이지당 AI 호출 수·비용을 측정하고, 그 결과로 페이지 제한과 작업자 수를 조정한다.

## 웹 전환 시 필수 구조 변경

현재 `app_server.py`는 로컬 단일 사용자용 공유 세션과 전역 작업 잠금을 사용한다. 파일 업로드도 base64를 JSON 본문에 넣고, 파싱 완료까지 요청 하나에서 기다린다. 이를 그대로 외부에 공개하지 않는다.

1. 업로드 → 작업 ID 발급 → 큐/워커 처리 → 상태 조회/결과 다운로드로 분리한다.
2. 사용자별 작업·파일 소유권을 검사하고 로그인/체험 횟수 제한을 적용한다.
3. 파일 크기뿐 아니라 PDF 페이지 수·렌더 픽셀·압축 해제 크기·실행 시간도 제한한다.
4. 파일 보존/삭제, 오류 재시도, 중복 요청 방지, 장애 시 작업 상태 복구를 설계한다.
5. 호스팅을 정한 뒤 업로드 경로를 결정한다. 예를 들어 Cloud Run의 HTTP/1 요청은 [32 MiB 상한](https://docs.cloud.google.com/run/quotas)이 있으므로 현재 64 MiB base64 JSON 방식을 그대로 유지하지 않는다. CPU·메모리 집약 작업은 [인스턴스 동시성](https://docs.cloud.google.com/run/docs/about-concurrency)을 낮게 시작하고 [메모리 사용량](https://docs.cloud.google.com/run/docs/configuring/services/memory-limits)을 계측한다.

## 다음 결정

- 우선 대상 문서와 파싱 품질 기준: 문항 누락, 두 문항 합침, 한 문항 분할, 지문 연결 오류의 허용치.
- 체험판이 JSON만 제공할지, crop/ZIP 다운로드까지 제공할지.
- 배포 방식(VM/컨테이너 서비스), 사용자 인증 방식, 저장 기간과 개인정보 고지.
- 기존 EDB 웹 전환 작업과 코어를 어떻게 공유할지. 이 제안은 그 작업을 자동으로 대체하거나 병합하지 않는다.
