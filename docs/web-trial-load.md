- 드로잉이 렌더 시간을 지배한다. 3쪽 기준 3000개/쪽이 Vercel 환산 12.9초, 4000개가 20.7초, 5000개부터 30초를 넘는다(31.4초; 위 §3-1 표). 체험판이 4쪽을 처리하게 되면서(42bd62c) 같은 밀도의 비용은 약 4/3배가 된다.
- 기본값을 `TRIAL_MAX_WORDS_PER_PAGE=4500`, `TRIAL_MAX_DRAWINGS_PER_PAGE=2500`으로 낮췄다(코드 `trial_input.DEFAULT_MAX_*`). 두 상한을 동시에 채운 4쪽 입력을 그 값 그대로 재면(2026-09-17, `GEMINI_API_KEY= .venv/bin/python scripts/trial_bench/complexity.py --words 4500 --drawings 2500 --pages 4`) render 5930 ms·segment 269 ms·assets 319 ms·total 6573 ms(문항 103개)로 Vercel 환산 **28.3초**다 -- "약 28초"는 assumption이 아니라 이 값이며, 2건이 겹쳐도 60초 안이다.
- 코퍼스가 13개 입력으로 넓어지면서 실제 시험지 최대도 달라졌다: 단어는 674 → **886**/쪽(`english_go2_hakpyeong_20260324.pdf`), 드로잉은 613/쪽(`2026학년도-수능-국어-언어와매체-홀수형.pdf`)으로 그대로다(2026-09-17, `~/edb-trial-bench/inputs/`의 13개 파일 전체를 아래 명령으로 다시 잼):
  ```
  GEMINI_API_KEY= .venv/bin/python -c "
  import pathlib
  from problem_parser import inspect_pdf
  from trial_input import DEFAULT_MAX_PAGES
  rows = [(p.name, inspect_pdf(p, max_pages=DEFAULT_MAX_PAGES)) for p in sorted(pathlib.Path.home().joinpath('edb-trial-bench', 'inputs').glob('*.pdf'))]
  ```

  출력은 `files: 13` / `max_words_per_page: 886` / `max_drawings_per_page: 613`이다. 상한 여유는 6배·4배가 아니라 4500÷886 ≈ **5.1배**, 2500÷613 ≈ **4.1배**다.
- 압축 콘텐츠 스트림 상한(`problem_parser.MAX_CONTENT_STREAM_RAW_BYTES_PER_PAGE`)도 1 MB에서 500 KB로 낮춰 한 요청의 일시적 팽창을 약 500 MB로 묶었다. 인식은 이제 파싱 슬롯 안에서 돌고(42bd62c) 인스턴스당 동시 파싱이 1이라 팽창은 인스턴스당 1건으로 제한된다.
- §3 본표는 다른 세션의 4쪽 변경이 커밋되기 전 4쪽 상태의 작업 트리에서 측정된 값이며, 42bd62c 이후의 HEAD와 같은 쪽수다.

## 4. 메모리 (로컬, `scripts/trial_bench/memory.py`)

기존 표는 버그였다: `max_rss_mb()`가 읽던 `resource.getrusage(RUSAGE_SELF).ru_maxrss`는 프로세스 생애 전체의 고점이라 한 번도 리셋되지 않는다. 한 프로세스에서 8개 파일을 순서대로 재면 각 행이 이전 행의 최댓값을 그대로 물려받아 61 → 1028 → 1172 → … → 1808 MB로 단조 증가하는, 개별 케이스와 무관한 숫자였다. `memory.py`를 고쳐 각 케이스를 `--worker`로 자기 자신을 재호출하는 새 자식 프로세스(겹치는 두 파싱을 수행하고 그 프로세스 자신의 peak RSS를 보고)에서 측정하도록 했다: 이제 한 행은 오직 그 파일 하나의 고립된 최댓값이고, 더는 의미가 없어진 `rss_before` 열은 없앴다.

### 4-2. 기준 대비 판정

기준은 2 GB의 60% = 1228.8 MB.

- 코퍼스 13행(3~4쪽, 두 파싱 겹침)은 800.8~1142.1 MB로 기준에 86.7~428.0 MB(7.1~34.8%) 여유가 있어 **통과**한다. 가장 빡빡한 행은 `social_saengwoon_2025suneung_9wolmopyeong_20240904.pdf`(사회탐구 4쪽) 1142.1 MB이고, 이 기계에만 있는 `01 물리학Ⅰ_문제지.pdf`(과학 4쪽 원본) 1130.5 MB·`01_물리학Ⅰ_문제지.pdf`(과학 3쪽 사본) 1043.8 MB가 뒤를 잇는다. 세 값의 간격(12~99 MB)은 아래 §4-4 "반복 노이즈"와 같은 자릿수이므로 어느 쪽이 진짜 더 빡빡한지 순서를 확정하지 않는다.
- 스펙 §6이 실제로 적은 최악 케이스는 "2×A3 **3쪽** PDF ... 2건 겹쳐"이지 4쪽이 아니다. `write_2xa3`와 동일한 지오메트리로 3쪽만 만든 `2xa3_3p.pdf`는 1097.3 MB로 기준을 131.5 MB(10.7%) 밑돈다 — **스펙이 정의한 2×A3 케이스는 통과한다.**
- `2xa3_4p.pdf`는 체험판의 실제 페이지 상한이 3→4로 올라간 것을 반영한, 스펙보다 한 단계 가혹한 별도 프로브다. 이번 §4-1의 단발 실행에서는 1221.4 MB로 기준을 7.4 MB(0.6%) 밑돌아 통과했지만, 여유가 노이즈 폭보다 작아 이 한 번의 값만으로는 판정할 수 없다 — 진짜 그림은 아래 §4-3의 12회 반복이다.

### 4-3. `2xa3_4p` 12회 반복 (2026-09-17, `GEMINI_API_KEY= .venv/bin/python scripts/trial_bench/memory.py --synthetic-2xa3 4 --repeat 12 --rss-threshold-mb 1228.8`)

12회 반복 시리즈에는 이를 재현할 코드가 없었다 — `memory.py`에 `--repeat`(케이스마다 여러 번 재고 min/median/mean/max 요약 한 줄을 찍는다)와 `--rss-threshold-mb`(그 요약에 기준 초과 횟수를 더한다) 옵션을 새로 추가해 위 명령으로 다시 쟀다. 12회 모두 1240.2~1287.4 MB(중앙값 1248.2 MB, 평균 1256.7 MB)로 **12회 중 12회** 기준(1228.8 MB)을 넘었다(최소 초과 11.4 MB/+0.9%, 최대 초과 58.6 MB/+4.8%). §4-1의 단발값 1221.4 MB는 이 12회 범위의 최솟값(1240.2 MB)보다도 낮다 — 즉 §4-1의 그 한 번은 노이즈의 유리한 쪽 극단을 뽑은 것이지, 이 케이스가 보통 기준 아래라는 뜻이 아니다. **스펙이 요구하지 않은, 더 가혹한 4쪽·2×A3 프로브는 반복 측정에서 일관되게 기준을 근소하게 넘는다.**

### 4-4. 반복 노이즈

같은 파일·같은 방식이라도 실행마다 수십 MB가 움직인다. `2xa3_4p.pdf` 자체가 한 세션 안에서도 §4-1의 단발값 1221.4 MB부터 §4-3의 12회 중 최댓값 1287.4 MB까지 66.0 MB(5.4%) 폭으로 움직였다. 코퍼스 파일도 마찬가지다: 직전 커밋의 표와 이번 §4-1 표를 같은 파일끼리 비교하면 `2025학년도-수능-국어-언어와매체-홀수형.pdf`가 884.7 → 900.0 MB로 15.3 MB(1.7%) 차이가 난다. §4-2·§4-3의 여유·초과 폭은 이 노이즈와 같은 자릿수라는 점을 감안해 읽어야 한다.

### 4-5. 동시성 1 대 2 — "절반" 주장을 측정으로 대체

단일 ÷ 겹침 비율은 16개 파일에서 **59.0~69.3%(중앙값·평균 63.7%)**로, 절반(50%)이 아니라 리뷰어가 잰 62~67%와 거의 겹친다. 즉 인스턴스당 파싱 1건(`TRIAL_PARSE_CONCURRENCY=1`, 현재 배포 기본값)에서의 실제 피크는 §4-1 표의 "절반"이 아니라 **약 60~70%**로 추정해야 한다 — 공유 라이브러리 로드 등 파싱 1건에도 드는 고정 비용이 있어 절반보다 높게 나오는 것으로 보인다.

- §4-1·§4-2·§4-3의 시나리오는 모두 `TRIAL_PARSE_CONCURRENCY=2`를 모델링한 것이다. 현재 배포 기본값은 `trial_config.py`의 `parse_concurrency: int = 1`이다. `TRIAL_PARSE_CONCURRENCY=2`를 켤지는 §6에서 아직 결정하지 않았다.
- **Vercel 실측과의 관계 — 비교 가능한 쌍이 아직 없다.** `docs/web-trial-spike-results.md`의 두 RSS 숫자는 각각 이런 측정이다.
  - **801 MB**(§2 표 "지구과학 원본" 행, §3 판단표가 "4쪽 801 MB"로 인용): 4쪽 과학 원본을 **한 번에 한 건씩 순차로** 호출한 웜 측정이다. 2건 겹침이 아니다.
  - **790 MB**(§2-2): 동시 10건에서 한 인스턴스에 2건이 겹쳤을 때의 값이지만, 입력은 **2026 9월 모평 국어 앞 3쪽**(일반 A4 3쪽)이다. 4쪽도 2×A3도 아니다.
  - 두 값 모두 스파이크 §2가 명시한 대로 "인스턴스 누적 최댓값(`ru_maxrss`)"이고 작은 파일부터 돌렸다 — 누적이라 801 MB 행은 바로 위 물리 원본 703 MB를 바닥에 깔고 있고, 그보다 낮은 값은 나올 수 없다(같은 이유로 §2 표에서 앞 행과 값이 같은 행은 "그 이하"로만 읽힌다). 이는 이 절 첫 문단이 로컬 표에서 걷어낸 바로 그 결함이므로, 두 숫자는 요청 하나의 피크에 대한 **상한**이지 피크 자체가 아니다. 상한이라도 값이 기준 아래이므로 "그 입력·시나리오에서 Vercel 요청 피크는 1.2 GB 아래였다"까지는 말할 수 있고, 그 이상은 말할 수 없다.
  - 그래서 이전 판의 "로컬 ÷ Vercel ≈ 1.39" 비율은 **삭제했다**. 시나리오(겹침 vs 단일)와 입력(2×A3 합성 vs 국어 3쪽, 과학 4쪽 vs 사회 4쪽)이 어긋난 쌍을 나눈 값이라 §2-3의 시간 비율(같은 파일·같은 시나리오)과 같은 종류의 환산 계수가 아니다. 두 쌍이 모두 1.39로 맞은 것은 우연이다. Vercel에서 같은 입력을 2건 겹쳐 요청 단위로 고립 측정하기 전에는 로컬·Vercel 메모리 배율을 쓸 수 없다.
- **종합**: 스펙 §6이 정의한 2×A3 3쪽·2건 겹침은 로컬 고립 측정에서 1097.3 MB로 1.2 GB 기준을 통과하고, §6이 함께 요구한 과학 4쪽(물리학Ⅰ 원본)도 1130.5 MB로 통과한다 — 여유는 각각 10.7%·8.0%다. 체험판이 상한을 4쪽으로 올리며 새로 가능해진, 스펙보다 가혹한 2×A3 4쪽 프로브는 `TRIAL_PARSE_CONCURRENCY=2`를 가정한 로컬 측정에서, 단발로는 통과할 때도 있지만(§4-1: +0.6% 여유) 12회 반복(§4-3)에서는 12회 모두 근소하게(+0.9~+4.8%) 넘는다. Vercel 쪽에는 이에 대응하는 **고립 측정이 아직 없다**(790·801 MB는 누적 `ru_maxrss` 상한이고 시나리오·입력도 다르다). 현재 배포 기본값(`parse_concurrency=1`)에서는 두 파싱이 애초에 겹치지 않고, §4-5의 실측에 따르면 그 실제 피크는 겹침 측정치의 절반이 아니라 **약 60~70%**로 추정된다. 정확한 진술은 **"고립 측정된 로컬 프록시에서 스펙 §6의 두 케이스는 통과하나 4쪽 2×A3 프로브는 반복 측정에서 일관되게 근소 초과이고, 현재 배포 기본값(`parse_concurrency=1`)에서는 두 파싱이 애초에 겹치지 않으며 그 실제 피크는 겹침 측정치의 약 60~70% 수준으로 추정된다. Vercel의 요청 단위 피크는 아직 재지 않았다"**이다.
